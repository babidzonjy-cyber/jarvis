# Jarvis CLI — Проектная Спецификация

Локальный голосовой ассистент-демон с push-to-talk, режимами work/chill,
на Go + PostgreSQL. Полностью офлайн (STT/LLM/TTS локально), кроссплатформенно
(macOS + Windows).

---

## 🎯 Идея

Один бинарник, одна команда — поднимается демон, слушает микрофон по хоткею
(push-to-talk, никакого постоянного прослушивания). Два режима:

- **work** — видит терминал/логи/git, помогает с разработкой, ничего лишнего
- **chill** — открывает программы, включает музыку, болтает, ничего про код

Переключение режимов — голосом или командой в терминале.

---

## 🔒 Принципы приватности (решаем ДО кода, не после)

1. **Push-to-talk, нc
   горячая клавиша (или между press-to-start / press-to-stop). Никакого
   фонового wake-word детектора на старте — это отдельная фича на будущее,
   когда будет доверие к системе.
2. **Всё локально по умолчанию.** STT (whisper.cpp), LLM (Ollama), TTS (Piper)
   — ничего не уходит в сеть. Внешний LLM API (Claude/GPT) — только если сам
   явно включишь флагом в конфиге, никогда не дефолт.
3. **Видимый индикатор состояния.** В терминале всегда видно `[LISTENING]`
   / `[IDLE]` / `[PROCESSING]` — никогда не должно быть неясности, слушает
   ли демон сейчас.
4. **Denylist для context gatherer (work-режим).** Никогда не читать `.env`,
   файлы с `secret`/`key`/`token` в имени, приватные ключи. Allowlist лучше
   чем denylist, но для старта хватит и denylist + явного списка папок,
   которые можно смотреть.
5. **Контроль над памятью.** Команда `jarvis forget` / `jarvis history clear`
   — должна существовать с первого дня, как только появляется история в БД.
6. **Подтверждение перед опасными действиями.** Любой tool, который реально
   что-то меняет в системе (`run_command`, деплой и т.д.) — спрашивает
   подтверждение в терминале перед выполнением, а не делает молча.

## 🛠 Технологии

| Категория | Инструмент | Кроссплатформенность |
|---|---|---|
| Язык | Go 1.23+ | ✅ |
| БД | PostgreSQL | ✅ (через Docker или локальную установку) |
| STT | whisper.cpp (Go-биндинги / exec) | ✅ есть сборки под macOS и Windows |
| LLM | Ollama (локально) | ✅ нативные клиенты под macOS/Windows |
| TTS | Piper | ✅ есть бинарники под обе ОС |
| Аудио захват | `github.com/gen2brain/malgo` (биндинги miniaudio) | ✅ кроссплатформенный, C-библиотека под капотом сама разруливает CoreAudio (macOS) / WASAPI (Windows) |
| Push-to-talk хоткей | `golang.design/x/hotkey` | ✅ поддерживает macOS и Windows из коробки |
| Tool-calling | нативно в Ollama | ✅ |

**Важно про кроссплатформенность:** самая рискованная часть — аудио захват
и глобальные хоткеи, т.к. это низкоуровневые OS API. Выбранные библиотеки
(`malgo`, `golang.design/x/hotkey`) уже абстрагируют разницу между macOS и
Windows — не потребуется писать свой код под каждую ОС отдельно. Но всё
равно закладывай время на тестирование именно этого куска на обеих
системах в первую очередь — тут чаще всего вылезают сюрпризы.

## 🏗 Архитектура (тот же принцип, что в прошлом проекте — слои по зависимостям)

```
User Voice / CLI command
        ↓
   audio (захват + hotkey)
        ↓
   pipeline (orchestrator: связывает stt → llm → tts)
        ↓
   service/transcribe → service/llm → service/tts
        ↓
   repository (Postgres: история, режимы, настройки)
```

### Структура папок

```
cmd/jarvis/
  main.go                    — entry point, поднимает всё одной командой

internal/
  domain/                    — Mode, Command, HistoryEntry, ToolCall (только структуры, без логики)

  repository/                — Postgres-слой
    mode_repository.go
    history_repository.go
    settings_repository.go

  service/
    transcribe/               — обёртка над whisper.cpp
    llm/                        — вызов Ollama, tool-calling loop
    tts/                         — обёртка над Piper
    mode/                         — логика переключения режимов
    tools/                        — реализация функций (open_app, run_command, read_logs, play_music...)
    context/                      — (только work) сборщик контекста из терминала/логов, allowlist/denylist

  pipeline/                   — orchestrator: audio → stt → llm → tts, один сквозной поток

  audio/
    capture.go                 — захват микрофона (malgo)
    hotkey.go                   — push-to-talk хоткей

  cli/                        — команды cobra: start, mode, status, history, forget

  logger/                     — slog, структурированное логирование

pkg/                          — пусто на старте

docker-compose.yaml            — только PostgreSQL
Dockerfile                     — опционально, если захочешь контейнеризовать демон (аудио/хоткеи из контейнера работать не будут — держи это в уме, демон, скорее всего, будет жить нативно на хосте, а Docker — только для БД)
Makefile
.env
go.mod / go.sum
README.md
```

### Правила зависимостей (как в прошлый раз)

- `domain/` не знает никого — только структуры данных
- `repository/` знает `domain/`, но не знает `service/`
- `service/` знает `repository/` и `domain/`, но не знает `pipeline/` или `cli/`
- `pipeline/` знает `service/`, оркеструет вызовы между ними
- `cli/` знает всё — точка входа для команд

## 🗄 PostgreSQL — черновая схема

```sql
modes (
  id, name, system_prompt, allowed_tools JSONB, created_at
)

history (
  id, mode, transcript, response, tool_calls JSONB, created_at
)

settings (
  key TEXT PRIMARY KEY, value TEXT
  -- текущий активный режим, пороги VAD, denylist-паттерны и т.д.
)
```

## 📝 Фазы разработки

### Phase 0 — Setup (день 1)
- [ ] `go mod init jarvis`
- [ ] Создать структуру папок как выше
- [ ] `docker-compose.yaml` только с PostgreSQL
- [ ] `.env`, `Makefile` (`make run`, `make docker-up`, `make docker-down`)
- [ ] Установить локально: Ollama, whisper.cpp (или его бинарник), Piper —
      проверить что все три реально работают из терминала сами по себе,
      ДО того как их подключать к Go-коду

### Phase 1 — STT-цикл (самый первый осязаемый результат)
- [ ] Захват аудио по хоткею через `malgo` (press-and-hold или start/stop)
- [ ] Сохранение записи во временный WAV
- [ ] Прогон через whisper.cpp
- [ ] Вывод текста в консоль
- [ ] Замерить задержку от конца речи до текста — это должно ощущаться
      быстрым, иначе весь опыт будет "тормозным"
- **Цель:** сказал фразу → увидел её текстом в терминале. Без LLM, без TTS.

### Phase 2 — CLI-каркас + режимы (без реальной логики внутри)
- [ ] `internal/domain` — структура Mode
- [ ] `internal/repository` — CRUD для режимов/настроек в Postgres
- [ ] `internal/cli` — команды `jarvis start`, `jarvis mode work/chill`, `jarvis status`
- [ ] Индикатор `[LISTENING]/[IDLE]` в консоли
- **Цель:** можешь переключать режимы командой, текущий режим хранится в БД.

### Phase 3 — LLM + tool-calling
- [ ] Подключение к Ollama (модель среднего размера, чтобы влезла по ресурсам —
      начни с чего-то небольшого, потом можно апгрейдить)
- [ ] Tool-calling loop в `service/llm`
- [ ] Первые 2-3 безобидных tool'а для обкатки механики: `get_time`,
      `run_command` (с обязательным подтверждением в терминале перед запуском)
- **Цель:** текст из Phase 1 идёт в LLM, LLM либо отвечает, либо вызывает tool.

### Phase 4 — TTS, замыкаем голосовой цикл
- [ ] Piper подключен через `service/tts`
- [ ] Ответ LLM озвучивается
- **Цель:** полный цикл хоткей → голос → текст → LLM → голос ответа работает
      end-to-end, без разрывов.

### Phase 5 — Наполнение режимов реальными фишками
- [ ] Work: `read_logs`, `run_git_status`, `check_process` — с denylist на
      секреты
- [ ] Chill: `open_app`, `play_music`, `search_web`
- [ ] Разные `system_prompt` под каждый режим — проверить, что тон и
      поведение реально ощутимо отличаются

### Phase 6 — Context gatherer (только work-режим)
- [ ] Фоновый сборщик контекста из терминала/логов (allowlist на папки/файлы)
- [ ] Проактивные голосовые уведомления при ошибках, с настраиваемым порогом
      чувствительности (чтобы не задалбывал каждой мелочью)

### Phase 7 — Приватность-полировка + производительность
- [ ] `jarvis forget` / `jarvis history clear`
- [ ] pprof-профилирование пайплайна (задержка STT/LLM/TTS по отдельности)
- [ ] Ревью: точно ничего не утекает в сеть по дефолту
- [ ] Проверка work на Windows отдельно (аудио + хоткеи — самое рискованное место)

### Phase 8 — Testing
- [ ] Unit-тесты на `service/mode` (переключение режимов)
- [ ] Unit-тесты на `service/llm` (роутинг tool-calls)
- [ ] Integration-тест на `repository` слой

## 🚀 С чего начать прямо сейчас

1. `go mod init jarvis`
2. Создать структуру папок из раздела "Архитектура"
3. Установить и проверить руками (вне Go) — Ollama, whisper.cpp, Piper —
   что все три работают сами по себе на твоей macOS
4. Начать с Phase 1 — захват звука и транскрипция, без всего остального

Дальше двигаешься фаза за фазой — каждая даёт рабочий, проверяемый кусок,
не нужно ждать до конца чтобы увидеть результат.
